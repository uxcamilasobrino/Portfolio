Agora Design System

Industry

EdTech

Role

Product Designer · Design System Designer

Team

Individual Project

Timeframe

6 weeks

Overview

EAE owns several digital products and experiences, including EAE Online, EAE Barcelona, EAE Madrid and EAE Corporate. As these products evolved independently, designers were solving similar problems in different ways. Components looked different, interactions behaved differently, and there were no shared rules defining how the interface should work. I designed Agora from scratch to create a shared foundation for the EAE ecosystem.

Challenge

Before Agora, there was no shared Design System connecting EAE's digital products. Designers were creating their own components and making individual decisions about visual styles, interaction states and component behavior. This created inconsistencies at different levels.

I already had a strong understanding of the EAE product ecosystem, so I used that knowledge as a starting point and complemented it with interviews with different designers. The objective was to identify:

  • What problems were repeated across products?
  • Which components were being recreated most often?
  • Which behaviors needed to become shared standards?
  • Which needs were genuinely specific to EAE?
  • Where could a shared system create value without restricting product teams?

Foundations

The brand guidelines provided by Marketing established the visual identity. My role was to translate that identity into a digital foundation that could support multiple products and interfaces.

Color

The red palette is particularly important because red is central to EAE's visual identity. Rather than treating the brand red as the only red available in the interface, I created a broader scale that allows different values to be used according to context. This creates more flexibility for UI states, backgrounds or borders.

Typography

The system uses Inter as its typeface. A structured hierarchy was established from H1 to H6, together with body text styles, creating consistent typographic relationships across products.

Icons

Agora includes a broad icon library organized into categories such as Arrow, Menu, Edit, Environment or Shape. The goal is to give designers a consistent visual vocabulary instead of recreating or sourcing icons independently.

Logo

The system also includes the EAE logo ecosystem, including the relevant light, dark, red and other variations.

Token architecture

Agora uses a three-level token structure that separates what a value is, what it means, and where it is used.

Brand

red/100

The underlying brand values.

→

Alias

primary/25

Contextual meaning — why a value is used.

→

Mapped

icons/default

Actual component usage — where it's applied.

Rather than directly connecting every component to a raw color value, this layering lets the system communicate why a value is being used, not just what it looks like — making it easier to maintain and giving future changes a clear path through the architecture.

Components

I prioritized components based on how frequently they appeared across the EAE ecosystem, starting with common building blocks like Button, Field, Menu, Checkbox, Switch, Tab Bar and Avatar, among others.

Each one is built with a set of shared properties — Status, Type, Icon Left, Icon Right, Label — so designers can create multiple configurations without needing a separate component for every variation.

Component example: Button

The Button component was one of the areas where the need for standardization was particularly visible. Agora defines a set of button types and interaction states, each treated as part of the system rather than a per-product decision:

It also supports icon variations, mobile configurations and button groups — instead of each product deciding independently how a button should behave, these decisions become part of the system.

Documentation

The Figma library holds the foundations, tokens and components, while Zeroheight documents how and when to use them — purpose, variants, states, and do's and don'ts — bridging the visual library with the knowledge needed to use it correctly.

Outcomes and learnings

The project has established:

  • A shared visual foundation
  • A structured token architecture
  • Reusable core components
  • Consistent component states and properties
  • EAE-specific components for educational workflows
  • A common approach to solving recurring interface problems
  • A foundation for future documentation and development

More importantly, design decisions that were previously made independently can now be represented as shared system decisions.

Learning

It was my first time building a Design System from scratch and having full ownership of the process. A Design System is much more than a component library.
